# Contributing to CME Taxonomy

This document describes the workflow for proposing, reviewing, and accepting new CME entries.

                └─────────────────┘

## Step-by-Step: Proposing New CME Entries

### 1. Run Gap Analysis (Local)

```bash
# Use the cme-discovery skill
claude /cme-discovery

# Or run manually
cd ~/.claude/skills/cme-discovery
bash osidb-cves.sh 90 /tmp/osidb-cves.json
python3 gap-analysis.py /tmp/osidb-cves.json ...
```

This generates candidate entries in JSON format.

### 2. Create Feature Branch

```bash
cd /path/to/cme
git checkout -b cme-proposals/$(date +%Y-%m-%d)
```

### 3. Save Proposals

Place generated entries in `data/proposals/`:

```bash
# Example: proposals generated by gap analysis
cp /tmp/cme-candidates/*.json data/proposals/
```

**Important:** Do NOT put proposals directly in `data/entries/` — use `data/proposals/` for the PR.

### 4. Commit and Push

```bash
git add data/proposals/
git commit -m "Propose 8 CME entries: Windows/macOS/K8s expansion

Gap analysis from 13,403 CVEs (90-day window).

Proposed entries:
- CME-808: LAPS (Windows credential rotation)
- CME-924: Arbitrary Code Guard (Windows)
- CME-925: WDAC (Windows application control)
- CME-305: macOS SIP (mandatory access control)
- CME-1318: LDAP Injection Prevention
- CME-1319: Deserialization Type Allowlisting
- CME-1012: USBGuard (USB device control)
- CME-209: Kubernetes NetworkPolicy"

git push origin cme-proposals/$(date +%Y-%m-%d)
```

### 5. Create Pull Request

On GitHub:
1. Go to https://github.com/stuwrtlttle/cme/pulls
2. Click "New pull request"
3. Select your branch: `cme-proposals/YYYY-MM-DD`
4. Add description with:
   - Gap analysis context (CVE count, date range)
   - Summary of proposed entries
   - Platform coverage impact
   - CWE coverage impact

### 6. Review Process

**Automated checks run:**
- ✅ Schema validation (`validate.yml`)
- ✅ Required fields check
- ✅ CME ID uniqueness check
- ✅ Filename matches `cme_id`

**Manual review:**
- CVSS impact rationale
- Verification command accuracy
- Platform applicability
- CWE relationship validity
- Duplicate check against existing entries

### 7. Merge to Main

When approved, merge the PR. **GitHub Actions automatically:**

1. **Validates proposals** against schema
2. **Moves** `data/proposals/*.json` → `data/entries/`
3. **Rebuilds static site** with new entries
4. **Commits changes** back to main
5. **Tags release** (e.g., `release-20260915-136-entries`)

The workflow is defined in `.github/workflows/accept-proposals.yml`.

### 8. VPS Deployment

SSH to VPS and run:

```bash
cd /path/to/cme
./scripts/deploy-vps.sh
```

This script:
- Pulls latest from GitHub
- Checks for entry changes
- Reseeds database if needed
- Restarts Docker services
- Verifies deployment

**Optional: Automated deployment via cron:**

```bash
# Add to VPS crontab
# Check for updates every 15 minutes
*/15 * * * * cd /path/to/cme && ./scripts/deploy-vps.sh >> /var/log/cme-deploy.log 2>&1
```

## Local Development Workflow

### Testing Proposals Locally

```bash
# Validate against schema
uv run python -m src.validate

# Preview static site locally
uv run python build_site.py
cd docs && python3 -m http.server 8080
# Open http://localhost:8080
```

### Rebuilding Static Site Manually

```bash
uv run python build_site.py
```

This generates HTML in `docs/` from:
- `data/entries/CME-*.json`
- `data/categories.json`
- `templates/*.html`

### Database Seeding (Docker)

```bash
# Fresh seed
docker compose down -v
docker compose up -d --build

# Reseed only
docker compose run --rm seed
docker compose restart server
```

## MCP Server vs GitHub Workflow

**❌ Don't use VPS MCP server for accepting proposals**

The MCP server on the VPS should be **read-only** for production. Using `propose_cme_entry()` on the VPS would:
- Create entries directly on VPS
- Bypass GitHub review process
- Cause VPS to diverge from GitHub source of truth

**✅ Correct workflow:**

1. **Local development** → Generate proposals
2. **GitHub PR** → Review and validate
3. **Merge to main** → Auto-accept and rebuild
4. **VPS deployment** → Pull from GitHub

## GitHub as Source of Truth

All state transitions happen via GitHub:

| State | Location | Managed By |
|-------|----------|------------|
| **Proposed** | `data/proposals/` | Developer PR |
| **Under Review** | PR on GitHub | Team review |
| **Accepted** | `data/entries/` | GitHub Actions (on merge) |
| **Published** | Static site `docs/` | GitHub Actions |
| **Deployed** | VPS database | Deployment script |

## CI/CD Workflows

### `.github/workflows/validate.yml`

Runs on: Every push and PR

- Validates all `data/entries/*.json` against schema
- Checks CME ID uniqueness
- Fails build if invalid

### `.github/workflows/accept-proposals.yml`

Runs on: Push to `main` with `data/proposals/CME-*.json`

- Validates proposals
- Moves to `data/entries/`
- Rebuilds static site
- Commits and pushes
- Tags release

### `.github/workflows/rebuild-site.yml`

Runs on: Manual trigger or changes to entries/templates

- Rebuilds static site from entries
- Commits if changes detected

### `.github/workflows/changelog.yml`

Runs on: Push to `main`

- Auto-generates changelog from commits
- Excludes `[skip ci]` and `[skip changelog]` commits

## Troubleshooting

### "Website still shows old entry count after deployment"

**Cause:** Static site not rebuilt by GitHub Actions

**Fix:**
```bash
# Manually trigger rebuild workflow on GitHub
# OR rebuild locally and commit:
cd /path/to/cme
uv run python build_site.py
git add docs/
git commit -m "Rebuild static site [skip ci]"
git push
```

### "VPS database has wrong entry count"

**Cause:** Database not reseeded after new entries added

**Fix:**
```bash
# On VPS:
cd /path/to/cme
docker compose run --rm seed
docker compose restart server

# Verify:
docker compose exec postgres psql -U cme -d cme -c "SELECT COUNT(*) FROM cme_entries;"
```

### "Proposal validation failed in PR"

**Cause:** Missing required fields or invalid JSON

**Fix:**
```bash
# Local validation
cd /path/to/cme
uv run python -m src.validate

# Check specific file
jq empty data/proposals/CME-XXX.json  # Validates JSON syntax
jq '.cme_id, .control_name, .evidence_state' data/proposals/CME-XXX.json
```

## Best Practices

1. **Always use feature branches** for proposals
2. **One proposal per CME entry** (atomic commits)
3. **Include gap analysis context** in PR description
4. **Test locally** before pushing
5. **Wait for CI** to pass before requesting review
6. **Deploy to VPS** after merge, not before
7. **Tag releases** for significant additions
8. **Document platform coverage** in commit messages
