CME-404

Certificate Pinning

Harden Application Unquantified evidence Preventive

Description

Restricts which TLS certificates a client or service will accept by pinning to a specific set of public keys (SPKI hashes), leaf certificates, or intermediate CA certificates, rather than trusting any certificate signed by any CA in the system trust store. Without pinning, compromise of any of hundreds of trusted CAs (or a misissued certificate from any CA) enables MitM — demonstrated by DigiNotar (2011), CNNIC subordinate (2015), and Symantec incidents. With pinning, the client deterministically rejects certificates whose public key hash does not match the pin set, even if the certificate is validly signed by a trusted CA. Pinning is deployed in three contexts: (1) mobile applications (Android Network Security Config trust-anchors, iOS TrustKit/URLSession pinning), (2) service-to-service communication (gRPC channel credentials, custom TLS verification callbacks), and (3) DNS-based pinning via DANE/TLSA records (RFC 6698). Browser-side HTTP Public Key Pinning (HPKP, RFC 7469) was deprecated and removed from Chrome in 2018 due to operational risk (pin rotation failures causing site lockout) — Certificate Transparency (CT) log monitoring is the modern browser-side equivalent for detecting rogue CA issuance. Pin rotation is the primary operational risk: if pins are not updated before certificate renewal, the application loses connectivity. Best practice is to pin to at least two keys (primary + backup) and pin to the intermediate CA rather than the leaf to survive routine certificate rotation.

CVSS Vector Impacts

Metric Transition Rationale
Attack Complexity (AC) L → H Without pinning, a network attacker who compromises any trusted CA (or obtains a misissued certificate from any CA in the default trust store) can present a validly-signed certificate and complete the TLS handshake — the client has no way to distinguish the rogue cert from the legitimate one. With pinning, the client compares the presented certificate's public key hash against the pinned set and rejects mismatches regardless of CA signature validity. The attacker must compromise the specific pinned private key, which is a fundamentally harder target than any-of-hundreds-of-CAs. Does not protect against compromise of the pinned key itself, and requires correct pin rotation to avoid self-inflicted outages

Verification

Verify certificate pinning is configured via DANE/TLSA records, application configuration, or connection-level SPKI hash validation
